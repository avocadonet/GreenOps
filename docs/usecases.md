### 1. Индексация Бизнес-требований (BR)
*Примечание: Индексация необходима для связывания Use Cases с бизнес-целями проекта.*

**Управление объектами и устройствами:**
* **BR-1.1**: Система должна обеспечивать регистрацию и иерархическое управление объектами (Здание → Помещение).
* **BR-1.2**: Система должна поддерживать регистрацию IoT-датчиков двух типов (COMMON - общедомовой, INDIVIDUAL - поквартирный) с защитой от двойной привязки.

**Сбор данных и мониторинг:**
* **BR-2.1**: Система должна принимать и сохранять телеметрию от IoT-датчиков в режиме реального времени через брокер сообщений.
* **BR-2.2**: Система должна предоставлять функционал настройки пороговых значений (UPPER / LOWER) для каждого датчика.
* **BR-2.3**: Система должна автоматически выявлять аномалии (OVERLOAD, LEAK) при выходе показаний за установленные пороги.

**Визуализация и аудит:**
* **BR-3.1**: Система должна предоставлять аналитические дашборды с графиками потребления и отображением статуса зданий в реальном времени.
* **BR-4.1**: Система должна вести неизменяемый журнал аудита всех инцидентов для разбора аварий.

**Инфраструктура:**
* **BR-5.1**: Инфраструктура системы должна быть контейнеризована и поддерживать технический мониторинг состояния сервисов (Grafana, Prometheus).

### 3. Use Cases (Сценарии использования)

**UC-1. Настроить новый объект мониторинга**

| Параметр | Описание |
| :--- | :--- |
| **Название** | UC-1. Настроить новый объект мониторинга |
| **Описание** | Администратор УК регистрирует здание, добавляет помещения, устанавливает датчики и задает пороги, чтобы система начала мониторинг объекта. |
| **Акторы** | Администратор УК (основной), Система (CRUD-сервис) |
| **Начальное состояние** | Система запущена; CRUD-сервис доступен; новое здание еще не зарегистрировано в БД. |
| **Триггер** | Администратор получил новый объект в управление и нажал кнопку "Добавить здание" в интерфейсе. |
| **Успешный сценарий** | 1. **Администратор** заполняет форму и нажимает "Сохранить".<br>2. **Система** сохраняет здание и возвращает `building_id`.<br>3. **Администратор** создает юниты (помещения), указывая полученный `building_id`.<br>4. **Система** сохраняет каждый юнит и возвращает `unit_id`.<br>5. **Администратор** создает COMMON-датчик здания через форму.<br>6. **Система** проверяет XOR-ограничение (запрет привязки и к юниту, и к зданию одновременно) и сохраняет датчик.<br>7. **Администратор** задает пороги UPPER и/или LOWER для датчика.<br>8. **Система** сохраняет пороги. Объект готов к мониторингу. |
| **Альтернативный сценарий** | **Альт. 1: Здание уже существует (ветвление от шага 1)**<br>1а. **Администратор** находит здание в BuildingsView.<br>1б. Сценарий продолжается с шага 3.<br><br>**Альт. 2: Пороги будут добавлены позже (ветвление от шага 7)**<br>7а. **Администратор** пропускает создание порогов.<br>7б. **Система** регистрирует датчики без порогов (мониторинг идет, но без генерации инцидентов). Сценарий завершается успешно. |
| **Негативный сценарий** | **Негативный: Нарушение XOR-ограничения (ветвление от шага 6)**<br>6а. **Администратор** в запросе указал и `building_id`, и `unit_id`.<br>6б. **Система** возвращает ошибку HTTP 422 (Unprocessable Entity).<br>6в. Сценарий прерван: датчик не создан, администратор должен исправить форму. |
| **Конечное состояние** | При успехе: Здание, юниты, датчики и пороги сохранены в PostgreSQL. При негативном исходе: Объект настроен частично, требуется корректировка данных. |
| **Критерии приемки** | Созданное здание появляется во вкладках BuildingTabs. XOR-ограничение для датчиков работает строго. Пороги привязаны к датчикам и отображаются в ThresholdsView. |
| **Связанные требования** | BR-1.1, BR-1.2, BR-2.2 |

**UC-2. Обработать входящую телеметрию и обнаружить аномалию**

| Параметр | Описание |
| :--- | :--- |
| **Название** | UC-2. Обработать входящую телеметрию и обнаружить аномалию |
| **Описание** | Workers-сервис читает показания из Kafka, сохраняет метрику в БД и создает инцидент при обнаружении выброса (превышении порогов). |
| **Акторы** | Workers-сервис (основной), IoT-датчик (инициатор), Kafka |
| **Начальное состояние** | Kafka работает; датчик и порог зарегистрированы в БД; Workers-сервис запущен и подписан на топик `telemetry.raw`. |
| **Триггер** | В топике `telemetry.raw` появляется новое JSON-сообщение от датчика. |
| **Успешный сценарий** | 1. **Workers** читает сообщение (`sensor_id`, `value`, `timestamp`).<br>2. **Workers** десериализует данные и сохраняет запись `Metric` в БД.<br>3. **Workers** загружает пороги датчика и передает значение в SpikeDetector.<br>4. **SpikeDetector** обнаруживает превышение UPPER-порога.<br>5. **Workers** атомарно (в одной транзакции) создает `PeakLoad` и `Incident` (тип OVERLOAD).<br>6. **Workers** публикует `IncidentCreatedEvent` в топик `incidents.created`.<br>7. **Audit-потребитель** фиксирует событие в логах. |
| **Альтернативный сценарий** | **Альт. 1: Значение в норме (ветвление от шага 4)**<br>4а. **SpikeDetector** не обнаруживает отклонений.<br>4б. Шаги 5-7 пропускаются. Успешное завершение.<br><br>**Альт. 2: Нарушение LOWER-порога (ветвление от шага 4)**<br>4а. **SpikeDetector** обнаруживает падение показаний ниже нормы.<br>4б. Создается инцидент типа LEAK. Сценарий продолжается с шага 6. |
| **Негативный сценарий** | **Негативный: Неизвестный датчик (ветвление от шага 2)**<br>2а. **Workers** не находит `sensor_id` в БД.<br>2б. Сообщение отклоняется, ошибка логируется, инцидент не создается.<br><br>**Негативный: Ошибка транзакции (ветвление от шага 5)**<br>5а. База данных недоступна, транзакция откатывается.<br>5б. Событие не публикуется в Kafka, offset не коммитится (сообщение будет обработано повторно). |
| **Конечное состояние** | При успехе: Запись метрики сохранена; при аномалии инцидент зафиксирован в БД и отправлен в Kafka. При ошибке: Состояние БД не изменено. |
| **Критерии приемки** | Каждое сообщение из Kafka сохраняется как `Metric`. При `value > threshold` создается инцидент. Если `value > threshold * 1.5`, severity инцидента = HIGH. |
| **Связанные требования** | BR-2.1, BR-2.3 |

| **Негативный сценарий** | **Негативный: API недоступен (ветвление от шага 2)**<br>2а. **Система** пытается загрузить данные, но сервер БД упал.<br>2б. **Система** выдает ошибку "Нет соединения с сервером".<br>2в. Сценарий прерван, диспетчер сообщает о проблеме админам (DevOps). |
| **Конечное состояние** | При успехе: Диспетчер локализовал проблему и принял меры. |
| **Критерии приемки** | Дашборд обновляет статусы зданий без ручной перезагрузки страницы. Переход от здания к конкретному датчику занимает не более 2 кликов. |
| **Связанные требования** | BR-3.1, BR-2.3 |

| **Успешный сценарий** | 1. **Администратор** открывает модальное окно.<br>2. **Администратор** вводит новое значение `limit_value` и нажимает "Сохранить".<br>3. **Система** отправляет PUT-запрос `/thresholds/{id}`.<br>4. **Система** валидирует данные и обновляет запись в PostgreSQL.<br>5. **Система** закрывает окно и обновляет таблицу на экране.<br>6. Workers-сервис использует новый порог при следующем сканировании метрик. |

| **Конечное состояние** | При успехе: Новое значение порога сохранено и сразу влияет на детекцию аномалий. |
| **Критерии приемки** | Вводимое значение проходит строгую валидацию (float, >0). Обновление применяется "на лету" без перезагрузки бэкенда. |
| **Связанные требования** | BR-2.2 |
