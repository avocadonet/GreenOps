# GreenOps — Аналитическая документация

## Обзор продукта

**GreenOps** — это микросервисная система мониторинга и оптимизации энергопотребления для объектов «умного города». Система принимает потоки данных от тысяч IoT-датчиков в реальном времени, автоматически выявляет аномалии (перегрузки, утечки, простои) и предоставляет операторам и аналитикам интерактивный дашборд для управления зданиями, анализа потребления и оперативного реагирования на инциденты. Архитектура построена на событийной модели (Kafka), с раздельным хранением оперативных данных (Redis) и исторических (PostgreSQL).

## Часть 1: User Stories

---

### US-01: Регистрация нового здания

**Я, как** администратор УК,
**хочу** зарегистрировать новое здание в системе мониторинга,
**чтобы** система начала собирать и хранить данные об энергопотреблении этого объекта

**Acceptance Criteria:**
- [ ] Форма регистрации принимает название здания и сохраняет его через `POST /buildings`
- [ ] После успешного создания система возвращает уникальный `building_id` (HTTP 201)
- [ ] Созданное здание немедленно отображается в `BuildingsView` и вкладках `BuildingTabs`
- [ ] При пустом названии API возвращает HTTP 422 с описанием ошибки валидации
- [ ] Новое здание доступно для привязки юнитов и датчиков сразу после создания

---

### US-02: Добавление помещения (юнита) к зданию

**Я, как** администратор УК,
**хочу** добавлять логические помещения (квартиры, офисы, этажи) к существующему зданию,
**чтобы** вести раздельный учёт потребления по помещениям, а не только по зданию в целом

**Acceptance Criteria:**
- [ ] Форма создания юнита требует обязательного указания `building_id`
- [ ] После создания юнит отображается в `UnitsView` с привязкой к зданию
- [ ] Попытка создать юнит без `building_id` возвращает HTTP 422
- [ ] Удаление здания блокируется или выполняется каскадно с явным предупреждением при наличии юнитов
- [ ] Юнит доступен для привязки `INDIVIDUAL`-датчиков сразу после создания

---

### US-03: Установка датчика на объект

**Я, как** администратор УК,
**хочу** зарегистрировать IoT-датчик и привязать его к зданию (COMMON) или помещению (INDIVIDUAL),
**чтобы** система начала принимать и обрабатывать телеметрию от этого датчика

**Acceptance Criteria:**
- [ ] Датчик типа `COMMON` принимает только `building_id`; поле `unit_id` должно быть пустым
- [ ] Датчик типа `INDIVIDUAL` принимает только `unit_id`; поле `building_id` должно быть пустым
- [ ] Попытка указать оба поля одновременно возвращает HTTP 422 с описанием XOR-ограничения
- [ ] Созданный датчик отображается в `SensorsView` с указанием типа и места привязки
- [ ] Датчик доступен для назначения порогов после регистрации

---

### US-04: Настройка порогов аномалий для датчика

**Я, как** администратор УК,
**хочу** задать верхний и нижний пороги нормального потребления для датчика,
**чтобы** система автоматически создавала инциденты при выходе показаний за допустимые границы

**Acceptance Criteria:**
- [ ] Порог типа `UPPER` задаёт максимально допустимое значение `limit_value`
- [ ] Порог типа `LOWER` задаёт минимально допустимое значение `limit_value`
- [ ] Для одного датчика можно создать оба типа порогов независимо
- [ ] Все пороги отображаются в `ThresholdsView` с привязкой к датчику и зданию
- [ ] Удаление порога через `DELETE /thresholds/{id}` прекращает детекцию по этому типу

---

### US-05: Просмотр текущего состояния зданий на дашборде

**Я, как** диспетчер (технический персонал УК),
**хочу** видеть сводный статус всех зданий на главном дашборде,
**чтобы** мгновенно замечать объекты с аномальным потреблением и оперативно реагировать

**Acceptance Criteria:**
- [ ] `DashboardView` отображает сводные карточки (`StatsCards`) по всем зданиям
- [ ] Здания с активными инцидентами визуально выделяются (цвет, иконка предупреждения)
- [ ] Данные отображаются без перезагрузки страницы при обновлении
- [ ] При недоступности API интерфейс показывает внятное сообщение об ошибке
- [ ] Переход к детальной странице здания выполняется кликом по карточке или вкладке

---

### US-06: Просмотр графика потребления за период

**Я, как** менеджер УК,
**хочу** просматривать графики потребления энергии по зданию за выбранный период,
**чтобы** анализировать тренды и обосновывать решения по оптимизации

**Acceptance Criteria:**
- [ ] Компонент `UsageChart` строит график для выбранного здания
- [ ] Доступна фильтрация по временному диапазону (день, неделя, месяц)
- [ ] График строится на основе данных `energy_balances` из PostgreSQL
- [ ] Переключение здания через `BuildingTabs` обновляет график без перезагрузки страницы
- [ ] При отсутствии данных за период отображается пустое состояние с подсказкой

---

### US-07: Автоматическое обнаружение перегрузки (OVERLOAD)

**Я, как** система мониторинга (Workers-сервис),
**хочу** автоматически создавать инцидент `OVERLOAD` при превышении верхнего порога,
**чтобы** диспетчер мог увидеть инцидент в интерфейсе и оперативно принять меры

**Acceptance Criteria:**
- [ ] При `value > threshold.limit_value` (тип `UPPER`) создаётся `Incident` типа `OVERLOAD`
- [ ] Одновременно создаётся запись `PeakLoad`; оба объекта сохраняются в одной транзакции
- [ ] Публикуется `IncidentCreatedEvent` в топик `incidents.created`
- [ ] При `value > limit_value * 1.5` severity инцидента устанавливается `HIGH`, иначе `LOW`
- [ ] Если порог не задан для датчика, инцидент не создаётся

---

### US-08: Автоматическое обнаружение утечки (LEAK)

**Я, как** система мониторинга (Workers-сервис),
**хочу** автоматически создавать инцидент `LEAK` при падении показаний ниже нижнего порога,
**чтобы** диспетчер своевременно выявлял нештатное снижение потребления

**Acceptance Criteria:**
- [ ] При `value < threshold.limit_value` (тип `LOWER`) создаётся `Incident` типа `LEAK`
- [ ] Инцидент содержит ссылки на датчик, порог и временну́ю метку события
- [ ] Публикуется `IncidentCreatedEvent` в топик `incidents.created`
- [ ] Если нижний порог для датчика не задан, инцидент `LEAK` не создаётся
- [ ] Инцидент доступен для просмотра через аналитический интерфейс после обработки

---

### US-09: Мониторинг средней нагрузки по датчику

**Я, как** менеджер УК,
**хочу** просматривать расчётные показатели средней нагрузки (`AverageLoad`) по датчикам,
**чтобы** оценивать базовый уровень потребления и выявлять отклонения от нормы

**Acceptance Criteria:**
- [ ] `AverageLoad` рассчитывается автоматически Workers-сервисом и сохраняется с привязкой к датчику
- [ ] Данные средней нагрузки доступны через API и отображаются в интерфейсе
- [ ] Значение обновляется при поступлении новых метрик
- [ ] Данные можно просмотреть в разрезе конкретного датчика и здания

---

### US-10: Симуляция потока данных от датчиков

**Я, как** DevOps-инженер,
**хочу** запускать симулятор IoT-устройств для проверки работы системы,
**чтобы** тестировать всю цепочку обработки данных без подключения реального оборудования

**Acceptance Criteria:**
- [ ] Команда `python simulator.py` запускает поток синтетических метрик
- [ ] Симулятор публикует данные в топик `telemetry.raw` через Kafka
- [ ] Workers-сервис корректно обрабатывает симулированные данные
- [ ] Изменения отображаются на дашборде в реальном времени в ходе симуляции
- [ ] Симулятор поддерживает сценарии с выбросами для тестирования `SpikeDetector`

---

### US-11: Мониторинг состояния инфраструктуры

**Я, как** SRE/DevOps-инженер,
**хочу** отслеживать технические метрики всех микросервисов через Grafana/Prometheus,
**чтобы** оперативно выявлять деградацию производительности и предотвращать сбои

**Acceptance Criteria:**
- [ ] Prometheus собирает метрики со всех контейнеров согласно `prometheus.yml`
- [ ] Grafana подключена к Prometheus и отображает дашборды состояния сервисов
- [ ] Метрики включают: RPS, latency, нагрузку CPU/памяти, Kafka consumer lag
- [ ] При падении сервиса его метрики становятся недоступными (visible failure)
- [ ] Весь стек поднимается одной командой `docker-compose up -d --build`

---

### US-12: Удаление устаревшего датчика

**Я, как** администратор УК,
**хочу** удалять демонтированные или замененные датчики из реестра,
**чтобы** поддерживать актуальность оборудования и не получать инциденты от несуществующих устройств

**Acceptance Criteria:**
- [ ] `DELETE /sensors/{id}` удаляет датчик и возвращает HTTP 204
- [ ] Связанные пороги (`Threshold`) удаляются вместе с датчиком
- [ ] Исторические метрики сохраняются в PostgreSQL для архивных целей
- [ ] Удалённый датчик исчезает из `SensorsView` немедленно
- [ ] Попытка удалить несуществующий датчик возвращает HTTP 404

Администратор указал и `building_id`, и `unit_id` одновременно<br>6б. **Система** возвращает HTTP 422 с описанием ошибки<br>6в. Сценарий прерван: датчик не создан, администратор исправляет форму |

| Критерии приёмки | Созданное здание появляется в `BuildingsView`. XOR-ограничение при создании датчика работает корректно. Пороги привязаны к датчику и отображаются в `ThresholdsView` |

### UC-02: Обработать входящую телеметрию и обнаружить аномалию

| Параметр | Описание |
| ----------------------- | ------------------------------------------------------------ |
| Название | UC-02. Обработать входящую телеметрию и обнаружить аномалию |
| Описание | Workers-сервис читает сообщение из Kafka, сохраняет метрику и создаёт инцидент при обнаружении выброса |
| Акторы | Workers-сервис (основной), IoT-датчик / Simulator (инициатор) |
| Начальное состояние | Kafka работает; датчик и его порог зарегистрированы в БД; Workers подписан на `telemetry.raw` |
| Триггер | В топике `telemetry.raw` появилось новое сообщение с показанием датчика |
| Успешный сценарий | 1. **Workers** читает JSON-сообщение (`sensor_id`, `value`, `timestamp`) из `telemetry.raw`<br>2. **Workers** десериализует DTO и сохраняет запись `Metric` в PostgreSQL<br>3. **Workers** загружает пороги датчика и передаёт значение в `SpikeDetector`<br>4. `SpikeDetector` обнаруживает превышение UPPER-порога<br>5. **Workers** атомарно создаёт `PeakLoad` и `Incident` типа `OVERLOAD` в одной транзакции<br>6. **Workers** публикует `IncidentCreatedEvent` в топик `incidents.created`<br>7. **Audit-потребитель** фиксирует событие в логах |
| Альтернативный сценарий | (Альт. 1: Значение в норме, ветвление от шага 4)<br>4а. `SpikeDetector` не обнаруживает отклонений<br>4б. Шаги 5–7 пропускаются<br>4в. Сценарий завершается успешно: только метрика сохранена<br><br>(Альт. 2: Нарушение LOWER-порога, ветвление от шага 4)<br>4а. `SpikeDetector` обнаруживает значение ниже порога<br>4б. Создаётся `Incident` типа `LEAK`<br>4в. Сценарий продолжается с шага 6 |
| Негативный сценарий | (Негативный: Неизвестный `sensor_id`, ветвление от шага 2)<br>2а. **Workers** не находит датчик в БД<br>2б. Метрика отклоняется, ошибка логируется<br>2в. Сценарий прерван: метрика и инцидент не созданы<br><br>(Негативный: Ошибка транзакции БД, ветвление от шага 5)<br>5а. **Workers** не может сохранить `PeakLoad` + `Incident`<br>5б. Транзакция откатывается; событие в Kafka не публикуется<br>5в. Сообщение остаётся в Kafka и будет повторно обработано |
| Конечное состояние | При успешном сценарии: `Metric` сохранена; при аномалии — `PeakLoad` и `Incident` созданы атомарно, событие опубликовано. При негативном: состояние БД не изменено |
| Критерии приёмки | Каждое входящее сообщение порождает запись `Metric`. При `value > limit_value` создаётся инцидент. Severity = HIGH при `value > limit * 1.5`. При неизвестном `sensor_id` система не падает |
| Связанные требования | Приём потока данных через API-шлюз (Must Have); гарантированная доставка через Kafka (Must Have) |

### UC-04: Скорректировать порог датчика

| Параметр | Описание |
| ----------------------- | ------------------------------------------------------------ |
| Название | UC-04. Скорректировать порог датчика |
| Описание | Администратор изменяет значение `limit_value` существующего порога под новый профиль нагрузки |
| Акторы | Администратор УК (основной), CRUD-сервис |

| Триггер | В топике `incidents.created` появилось новое событие `IncidentCreatedEvent` |
| Успешный сценарий | 1. **AuditConsumer** читает сообщение из `incidents.created`<br>2. **AuditConsumer** десериализует `IncidentCreatedEvent` через Adaptix `Retort`<br>3. **AuditConsumer** записывает в лог: тип инцидента, severity, `sensor_id`, timestamp<br>4. **AuditConsumer** коммитит Kafka offset — сообщение считается обработанным |
| Альтернативный сценарий | (Альт. 1: Потребитель перезапустился, ветвление от шага 1)<br>1а. **Kafka** повторно доставляет непрочитанные сообщения (at-least-once)<br>1б. **AuditConsumer** обрабатывает их повторно<br>1в. Лог может содержать дублирующие записи (idempotency не критична для аудита) |
| Негативный сценарий | (Негативный: Сообщение не десериализуется, ветвление от шага 2)<br>2а. `IncidentCreatedEvent` содержит неизвестные поля или некорректный формат<br>2б. **AuditConsumer** логирует предупреждение с деталями сообщения<br>2в. Offset всё равно коммитится, чтобы не блокировать обработку следующих сообщений<br>2г. Сценарий прерван для данного сообщения: запись в лог не создана |
| Конечное состояние | При успешном сценарии: инцидент зафиксирован в логах; архитектура готова к расширению (webhook, ITSM). При негативном: данное сообщение пропущено; прочие сообщения продолжают обрабатываться |
| Критерии приёмки | Каждый `IncidentCreatedEvent` порождает запись в логе. Некорректные сообщения не блокируют consumer group. Offset коммитится в обоих случаях |
| Связанные требования | Гарантированная доставка через Kafka (Must Have) |
