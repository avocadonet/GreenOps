# GreenOps — Руководство по ролям пользователей

Каждый пользователь получает роль **в рамках конкретной организации**. Один человек может иметь разные роли в разных УК. Роль назначается владельцем организации или платформенным администратором.

---

## Быстрая сводка

| Роль | Кто это | Что может |
|---|---|---|
| `SUPER_*` | Команда GreenOps | Всё на платформе |
| `ORGANIZATION_OWNER` | Владелец УК | Всё внутри своей организации, кроме управления ролями платформы |
| `ADMIN` | Технический администратор УК | Полное управление инфраструктурой (здания, датчики, пороги) |
| `REDACTOR` | Диспетчер / энергоаудитор | Чтение инфраструктуры + управление порогами аномалий |
| `OWNER` | Наблюдатель / руководитель | Только чтение: данные, аналитика, пороги |
| `PUBLIC` | Зарегистрированный, без роли | Нет доступа ни к каким данным |

---

## Подробные профили

---

### ORGANIZATION_OWNER — Владелец организации

**Кто:** Руководитель управляющей компании, создавший организацию на платформе.

**Типичные задачи:**
- Зарегистрировал организацию → автоматически получил эту роль
- Приглашает сотрудников и назначает им роли (`ADMIN`, `REDACTOR`, `OWNER`)
- Может изменить реквизиты организации или удалить её

**Что разрешено:**

| Раздел | Просмотр | Создание | Редактирование | Удаление |
|---|:---:|:---:|:---:|:---:|
| Организация | ✓ | — | ✓ | ✓ |
| Здания | ✓ | ✓ | ✓ | ✓ |
| Юниты | ✓ | ✓ | ✓ | ✓ |
| Датчики | ✓ | ✓ | ✓ | ✓ |
| Пороги | ✓ | ✓ | ✓ | ✓ |
| Балансы / аналитика | ✓ | — | — | — |
| Роли пользователей | — | — | — | — |

> Управление ролями (`CAN_*_ROLE`) доступно только платформенным `SUPER_*` аккаунтам.

---

### ADMIN — Технический администратор

**Кто:** Инженер или ответственный за эксплуатацию, который настраивает физическую инфраструктуру.

**Типичные задачи:**
- Регистрирует новое здание при вводе объекта в эксплуатацию
- Добавляет юниты (подъезды, квартиры, этажи)
- Подключает датчики и привязывает их к зданию или юниту
- Указывает `external_id` и провайдера (например, Tuya) при регистрации датчика, чтобы адаптер начал получать данные
- Задаёт и корректирует пороги аномалий — верхний (`UPPER`) и нижний (`LOWER`) для каждого тарифного периода

**Что разрешено:**

| Раздел | Просмотр | Создание | Редактирование | Удаление |
|---|:---:|:---:|:---:|:---:|
| Организация | — | — | — | — |
| Здания | ✓ | ✓ | ✓ | ✓ |
| Юниты | ✓ | ✓ | ✓ | ✓ |
| Датчики | ✓ | ✓ | ✓ | ✓ |
| Пороги | ✓ | ✓ | ✓ | ✓ |
| Балансы / аналитика | ✓ | — | — | — |

**На что обратить внимание:**
- При создании датчика нужно указать либо здание (`COMMON`), либо юнит (`INDIVIDUAL`) — одновременно оба поля выставить нельзя.
- Поле `external_id` + провайдер (например, `tuya`) — это то, что связывает физический прибор с записью в системе. Без них данные от устройства не поступят.

---

### REDACTOR — Диспетчер / Энергоаудитор

**Кто:** Оперативный персонал, который ежедневно мониторит потребление и реагирует на инциденты. Также подходит для роли энергоаудитора, который не управляет инфраструктурой, но настраивает пороги.

**Типичные задачи:**
- Отслеживает дашборд — видит все здания и текущие аномалии
- При обнаружении инцидента (`OVERLOAD`, `LEAK`) принимает оперативные решения
- Корректирует пороги без согласования с администратором (например, сезонная корректировка)
- Может настроить уведомления на Telegram в личном кабинете

**Что разрешено:**

| Раздел | Просмотр | Создание | Редактирование | Удаление |
|---|:---:|:---:|:---:|:---:|
| Здания | ✓ | — | — | — |
| Юниты | ✓ | — | — | — |
| Датчики | ✓ | — | — | — |
| Пороги | ✓ | ✓ | ✓ | ✓ |
| Балансы / аналитика | ✓ | — | — | — |

**Ограничения:**
- Не может добавлять или удалять здания, юниты, датчики — только читать их.
- Не имеет доступа к настройкам организации и пользователям.

---

### OWNER — Наблюдатель

**Кто:** Руководитель или представитель заказчика, которому нужен доступ к данным без права что-либо изменить. Также подходит для роли жильца, когда функциональность для жильцов будет реализована.

**Типичные задачи:**
- Просматривает аналитику потребления по зданиям
- Видит текущие пороги и баланс энергии
- Готовит данные для отчётов перед надзорными органами

**Что разрешено:**

| Раздел | Просмотр | Создание | Редактирование | Удаление |
|---|:---:|:---:|:---:|:---:|
| Здания | ✓ | — | — | — |
| Юниты | ✓ | — | — | — |
| Датчики | ✓ | — | — | — |
| Пороги | ✓ | — | — | — |
| Балансы / аналитика | ✓ | — | — | — |

> Полностью read-only роль. Никакие изменения через интерфейс или API недоступны.

---

### PUBLIC — Без роли

**Кто:** Зарегистрированный пользователь, которому ещё не назначена роль ни в одной организации.

**Что разрешено:** Ничего. Доступна только собственная учётная запись (изменение пароля, профиля).

**Что делать:** Обратиться к `ORGANIZATION_OWNER` или `ADMIN` своей УК для получения роли.

---

### SUPER_USER / SUPER_OWNER / SUPER_ADMIN / SUPER_REDACTOR — Платформенные роли

**Кто:** Внутренняя команда GreenOps. Эти роли не назначаются клиентам.

Все четыре роли имеют одинаковый набор прав — полный доступ ко всем сущностям всех организаций, включая управление ролями (`CAN_*_ROLE`). Различие — в приоритете при разрешении конфликтов и административных операциях:

`SUPER_USER` > `SUPER_OWNER` > `SUPER_ADMIN` > `SUPER_REDACTOR`

## Типичные сценарии назначения ролей

**Ввод нового объекта в эксплуатацию**
1. `ORGANIZATION_OWNER` или `ADMIN` создаёт здание → добавляет юниты → регистрирует датчики с `external_id` и провайдером.
2. Адаптер автоматически начинает опрашивать устройство и публиковать данные.
3. `ADMIN` задаёт пороги для каждого датчика.

**Ежедневный мониторинг**
1. `REDACTOR` заходит на дашборд → видит список зданий с визуальными маркерами инцидентов.
2. Открывает проблемное здание → анализирует последние показания датчиков.
3. При необходимости корректирует порог прямо из интерфейса.

**Предоставление доступа новому сотруднику**
1. `ORGANIZATION_OWNER` переходит в раздел пользователей.
2. Находит зарегистрированного пользователя (или приглашает по email).
3. Назначает роль в соответствии с должностью: `ADMIN` для инженера, `REDACTOR` для диспетчера, `OWNER` для руководства.
