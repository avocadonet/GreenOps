# GreenOps — Тезисы для презентации

> Заметки докладчика для обзора планирования проекта.  
> Аудитория: техническая команда + стейкхолдеры.

---

## О чём проект

- GreenOps — платформа мониторинга энергопотребления для умного города: принимает телеметрию от датчиков в реальном времени через Kafka, обнаруживает аномалии (перегрузки и утечки), ежедневно вычисляет потери энергии по зданиям и отображает всё через дашборд Vue 3 — на базе микросервисной архитектуры FastAPI
- Ключевая ценность — автоматическое выявление «коммерческих потерь»: разница между показаниями общедомового счётчика и суммой показаний поквартирных счётчиков, 24/7, без ручного вмешательства

## Разбор диаграммы Ганта

- **Дни 1–2:** Вся команда в режиме планирования — аналитик и архитектор работают параллельно; код ещё не пишется
- **Дни 3–4:** Команда расходится по направлениям: DB-инженер занимается схемой, DevOps поднимает Docker, фронтенд начинает макеты, бэкенд пишет API-контракты
- **Дни 5–9 (критический спринт фундамента):** Здесь строятся Shared Kernel, библиотека crudx, доменный слой и авторизация; большинство последующих задач заблокированы до их завершения; это самая рискованная неделя
- **Дни 10–16 (спринт разработки):** Все четыре потока работают в полном параллельном режиме — самый насыщенный и продуктивный период; диаграмма Ганта здесь наиболее широкая
- **Дни 17–19:** Интеграционные и юнит-тесты компактно завершают основной спринт; документация идёт параллельно; E2E-тестирование, исправление ошибок и деплой следуют на днях 20–22

**Ключевые наблюдения по параллельным потокам:**
- Поток фронтенда (FE Dev) полностью независим от бэкенда после 8-го дня — API-клиент уже типизирован по контрактам
- Поток DevOps (Docker, Nginx, Prometheus) имеет 9–13 дней резерва — никогда не окажется на критическом пути
- Бэкенд-разработчик полностью сериализован с 7-го по 17-й день — одна задача должна завершиться прежде, чем начнётся следующая; параллелизация невозможна

## Разбор PERT-диаграммы

- Каждый узел PERT содержит три оценки времени: оптимистичную, наиболее вероятную и пессимистичную. Ожидаемое время — взвешенное среднее: `(мин + 4×вер + макс) / 6`
- **Задачи с высокой дисперсией** (σ² = 0.25) — там, где оценки наименее надёжны:
  - T-10 библиотека crudx (собственная внутренняя библиотека, новый дизайн)
  - T-12 система аутентификации (логика безопасности склонна к расширению)
  - T-13 прикладной слой CRUD (6 сервисов + матрица разрешений + калькуляторы)
  - T-15 API-слой CRUD (наибольший объём инфраструктурного кода в проекте)
  - T-24 DashboardView (сложный stateful Vue-компонент)
  - T-31 интеграционное тестирование (результат зависит от плотности багов)
- **Задачи с низкой дисперсией** (σ² ≤ 0.063) надёжны и быстры: миграции, доменный слой, задачи планировщика, Nginx, симулятор
- PERT-ожидаемая длительность критического пути — **20.25 дня** при номинальном плане 19 дней; дельта +1.25 дня

## Объяснение критического пути

```
T-01/T-02 → T-04 → T-07 → T-11 → T-12 → T-13 → T-15 → T-16 → T-17 → T-32
```

- Критический путь целиком проходит через **разработку бэкенда** — не фронтенд, не DevOps
- Он представляет минимальную последовательность, которую нельзя сократить без распределения задач между несколькими разработчиками или сокращения объёма
- **Любое однодневное отставание на T-13 (прикладной слой) или T-15 (API-слой) напрямую сдвигает дату сдачи**
- T-07 (Shared Kernel) — первая «точка слияния»: именно здесь сходятся все потоки, и задержка на 1 день одновременно задерживает все зависимые задачи
- Вероятностный расчёт PERT показывает лишь **~15% шанс** завершить интеграционное тестирование к 25 апреля при реалистичных оценках

## Ключевые риски и узкие места

### 🚨 Критические риски

1. **Бутылочное горло: один человек на весь критический путь**
   - Десять из девятнадцати задач критического пути назначены одному бэкенд-разработчику
   - Болезнь, переключение контекста или любая недооценка на T-13 или T-15 немедленно каскадирует
   - Меры: назначить DevOps-инженера на T-14 (DB-репозитории) с 14 апреля для параллелизации этой недели

### ⚠️ Умеренные риски

2. **Библиотека crudx имеет запас лишь в 1 день**
   - Это внутренняя библиотека, не сторонняя зависимость
   - Если реализация займёт 4 дня вместо 3 — она входит в критический путь
   - Меры: упростить начальный объём (меньше вариантов декораторов, без transaction mixin на первом этапе)

3. **T-13 (прикладной слой CRUD) — крупнейшая задача, больше всего зависимостей**
   - Оценка 3 дня, максимум 5 — именно здесь вероятность проскальзывания наиболее высока
   - Включает 6 сервисов + систему разрешений + два калькулятора
   - Если займёт 4 дня — T-15 (API-слой) стартует на день позже и интеграционные тесты сдвигаются на 28 апреля — за дедлайн

4. **Сложность системы авторизации (T-12)**
   - JWT + bcrypt + RBAC-провайдер разрешений — оценка 2 дня
   - Системы авторизации регулярно расширяются: ротация refresh-токенов, крайние случаи в наследовании ролей, поток активации
   - Меры: зафиксировать объём точно по кодовой базе — без эндпоинта обновления токенов, без email-активации в этом спринте

5. **Задачи на критическом пути захватывают выходные**
   - T-15 (API-слой) выполняется 17–18 апр, затем 21 апр — промедление в пятницу стоит 2 календарных дня
   - T-26 (UsageChart) имеет ту же уязвимость
   - Меры: проводить код-ревью по средам/четвергам, чтобы выявлять блокеры до выходных

### ℹ️ Низкие риски (для сведения)

6. **У фронтенда 3 дня резерва — но они не «свободные»**
   - Все 3 дня будут израсходованы, если T-15 (API-слой) запоздает и FE не сможет завершить интеграцию
   - Фронтенд-разработчик должен использовать резерв для разработки на мок-данных и переключиться на реальный API, когда T-15 будет готов

7. **Нет выделенного окна для исправления ошибок в основном спринте**
   - T-35 (исправление ошибок) следует за E2E-тестированием в финальные дни проекта
   - Если интеграционное тестирование (T-32) обнаружит критические баги, времени на их исправление до начала E2E не будет
   - Меры: провести лёгкий дымовой тест после T-17, чтобы выявить баги на день раньше
