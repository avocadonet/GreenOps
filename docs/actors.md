# GreenOps — Акторы и их роли

---

## Стейкхолдеры

| Стейкхолдер | Сегмент | Заинтересованность | Взаимодействие с MVP |
|---|---|---|---|
| Управляющая компания (УК) | Внешний клиент | Высокая | Прямое — основной пользователь системы |
| Технический персонал УК (Диспетчеры) | Внешний пользователь | Средняя | Прямое — ежедневная работа в интерфейсе |
| Муниципалитет / Ситуационный центр | Внешний заказчик | Высокая | Косвенное — получает агрегированные данные |
| Жильцы | Внешний | Высокая | Не реализовано в MVP (запланировано) |
| Команда разработки | Внутренний | Высокая | Прямое — разработка и поддержка |
| Инвестор / Руководство | Внутренний | Высокая | Косвенное — метрики продукта |

## Ролевая модель (RBAC)

Система реализует многоуровневое разграничение доступа. Каждый пользователь имеет роль в рамках конкретной организации (`UserOrganizationRole`) — один пользователь может иметь разные роли в разных УК.

### Платформенные роли (GreenOps)

| Роль | Описание |
|---|---|
| `SUPER_USER` | Полный доступ ко всей платформе, включая все организации |
| `SUPER_OWNER` | Владелец платформенного аккаунта GreenOps |
| `SUPER_ADMIN` | Администрирование платформы: управление организациями и пользователями |
| `SUPER_REDACTOR` | Редакторские права на уровне платформы |

### Организационные роли (в рамках УК)

| Роль | Описание | Соответствует актору |
|---|---|---|
| `OWNER` | Полный контроль над организацией, максимальный приоритет | Руководитель УК |
| `ADMIN` | Управление инфраструктурой: здания, датчики, пороги, роли | Администратор УК |
| `REDACTOR` | Просмотр и редактирование данных, реагирование на инциденты | Диспетчер УК |
| `PUBLIC` | Только чтение — доступ к дашборду и аналитике | Менеджер УК |

### Приоритет ролей

Роли упорядочены по приоритету (`roles_priorities`): `SUPER_USER` > `SUPER_OWNER` > `SUPER_ADMIN` > `SUPER_REDACTOR` > `OWNER` > `ADMIN` > `REDACTOR` > `PUBLIC`. Пользователь с более высоким приоритетом может управлять пользователями с более низким.

## Система аутентификации

| Механизм | Реализация |
|---|---|
| Протокол | JWT (HS256) |
| Токены | Access token (1 час) + Refresh token (30 дней) |
| Пароли | bcrypt + случайная соль (32 байта, base64) |
| Активация | Email с токеном активации (`UserActivationToken`) |
| Уведомления | `EMAIL` или `TELEGRAM` (выбирается в `UserSettings`) |
| Telegram | Интеграция через `TelegramToken` (опционально) |

## Человеческие акторы (MVP)

---

### Руководитель УК (роль: `OWNER`)

**Ответственность:** Владелец организационного аккаунта. Управляет составом пользователей и назначает роли внутри своей УК.

**Действия:**
- Регистрирует организацию (УК) на платформе
- Приглашает сотрудников и назначает им роли (`ADMIN`, `REDACTOR`, `PUBLIC`)
- Понижает или отзывает роли в пределах своего приоритета
- Имеет все права `ADMIN`

**Точки входа:** Личный кабинет, REST API (`/users`, `/roles`)

---

### Администратор УК (роль: `ADMIN`)

**Ответственность:** Первоначальная настройка объектов и поддержание актуальности реестра оборудования.

**Действия:**
- Регистрирует здания, юниты (подъезды, квартиры, этажи), датчики
- Удаляет устаревшее оборудование из реестра
- Контролирует соблюдение XOR-ограничения при привязке датчиков (COMMON → здание, INDIVIDUAL → юнит)
- Задаёт и корректирует пороги аномалий (`UPPER` / `LOWER`) для датчиков

**Точки входа:** `BuildingsView`, `UnitsView`, `SensorsView`, `ThresholdsView`, REST API (`/buildings`, `/units`, `/sensors`, `/thresholds`)

---

### Диспетчер (роль: `REDACTOR`)

**Ответственность:** Непрерывный мониторинг состояния объектов и оперативное реагирование на инциденты.

**Действия:**
- Отслеживает текущий статус зданий на главном дашборде
- Обнаруживает здания с активными инцидентами (`OVERLOAD`, `LEAK`) по визуальным маркерам
- Переключается между зданиями через `BuildingTabs` для детального анализа
- Принимает оперативные решения — вызов аварийной службы, переключение нагрузки
- Может настроить уведомления на `TELEGRAM` через `UserSettings`

**Точки входа:** `DashboardView`, `BuildingTabs`, `SensorsView`

---

### Менеджер УК (роль: `PUBLIC`)

**Ответственность:** Анализ потребления по объектам, выявление коммерческих потерь и подготовка отчётов.

**Действия:**
- Анализирует графики потребления за выбранные периоды
- Сравнивает показатели между зданиями для выявления аномалий
- Работает с данными `EnergyBalance` и `AverageLoad`
- Формирует данные для отчётов перед руководством и надзорными органами

**Точки входа:** `DashboardView`, `UsageChart`, аналитический API

---

### DevOps / SRE-инженер (роль: `SUPER_ADMIN`)

**Ответственность:** Развёртывание, эксплуатация и мониторинг инфраструктуры платформы.

**Действия:**
- Разворачивает систему через `docker-compose up -d --build`
- Запускает и контролирует миграции БД (`alembic upgrade head`)
- Мониторит состояние сервисов через Grafana / Prometheus
- Настраивает алерты на деградацию сервисов
- Управляет конфигурацией JWT (`TokenConfig`: secret_key, алгоритм, время жизни токенов)

**Точки входа:** Docker Compose, Grafana, Prometheus, CLI

---

### QA-инженер

**Ответственность:** Сквозное тестирование работоспособности системы без реального оборудования.

**Действия:**
- Запускает симулятор IoT-данных (`simulator.py`)
- Генерирует сценарии с выбросами для проверки `SpikeDetector`
- Верифицирует цепочку: Kafka → Workers → PostgreSQL → API → Frontend
- Проверяет аутентификационный поток: регистрация → активация → логин → токен

**Точки входа:** CLI (`simulator.py`), `DashboardView`, PostgreSQL (прямые запросы)

## Системные акторы

---

### IoT-датчик / Sensor Simulator

**Тип:** Внешний источник данных

**Роль:** Генерирует поток телеметрии и публикует JSON-сообщения в Kafka-топик `telemetry.raw`.

**Взаимодействие:** Только исходящее — публикация в `telemetry.raw`. Не имеет обратного канала от системы.

**Формат сообщения:** `{ sensor_id, value, timestamp }`

---

### Workers-сервис (TelemetryConsumer)

**Тип:** Автоматизированный внутренний актор

**Роль:** Основной процессор данных. Принимает сырую телеметрию, персистирует метрики, детектирует аномалии и публикует события.

**Действия:**
- Читает из `telemetry.raw`, сохраняет `Metric` в PostgreSQL
- Вызывает `SpikeDetector` для проверки порогов
- Атомарно создаёт `PeakLoad` + `Incident` при обнаружении аномалии
- Публикует `IncidentCreatedEvent` в `incidents.created`

**Типы инцидентов, которые создаёт:**

| Условие | Тип инцидента | Severity |
|---|---|---|
| `value > threshold.limit_value` (UPPER) | `OVERLOAD` | HIGH если `value > limit * 1.5`, иначе LOW |
| `value < threshold.limit_value` (LOWER) | `LEAK` | HIGH если `value > limit * 1.5`, иначе LOW |
| `value ≈ 0` дольше 600 сек | `IDLE` | — (отложено, MVP trade-off) |

---

### Workers-сервис (AuditConsumer)

**Тип:** Автоматизированный внутренний актор

**Роль:** Подписчик топика `incidents.created`. Фиксирует факт инцидента в логах аудита. Служит точкой расширения для будущих интеграций (webhook, email, ITSM).

**Взаимодействие:** Только чтение из `incidents.created`; side-effect — запись в лог.

---

### CRUD-сервис

**Тип:** Внутренний сервис-актор (Control Plane)

**Роль:** Единственный сервис, управляющий конфигурационными сущностями, пользователями, аутентификацией и выполняющий миграции БД.

**Управляет сущностями:** `Building`, `Unit`, `Sensor`, `Threshold`, `User`, `UserOrganizationRole`

**Особые полномочия:**
- Запускает `alembic upgrade head` при старте (через `migrations.dockerfile`)
- Единственный сервис с правом записи в таблицы конфигурации и пользователей
- Выдаёт JWT access/refresh токены (`JwtTokensGateway`)
- Хэширует пароли через bcrypt + соль (`BcryptSecurityGateway`)

---

### Nginx

**Тип:** Инфраструктурный актор

**Роль:** Reverse Proxy и единая точка входа. Маршрутизирует HTTP-трафик от пользователей к нужному микросервису.

**Взаимодействие:** Принимает все внешние запросы; прозрачен для остальных акторов.
