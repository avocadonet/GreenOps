
# Детальный план проекта: Стабильный запуск тестов на задачи (manytask/checker)

**Глобальная цель:** Обеспечить стабильный, масштабируемый и унифицированный запуск тестов для задач, написанных на разных языках программирования, с прозрачным флоу от приватного репозитория админа до воркеров.

## Фаза 1: Анализ (Research & Discovery)
*Цель: Понять текущее устройство `manytask/checker`, выявить узкие места и спроектировать новую архитектуру.*

*   **Задача 1.1: Аудит текущего пайплайна Manytask.**
    *   Изучить код `manytask/checker` и смежных сервисов.
    *   Отрисовать текущую схему: как код попадает от студента -> как Manytask триггерит проверку -> как запускается контейнер -> как возвращается результат.
*   **Задача 1.2: Выявление узких мест (Bottlenecks).**
    *   Собрать метрики или проанализировать логи: где теряется время? (Долгий билд Docker-образов? Очереди сообщений? Сетевые задержки при скачивании тестов?).
    *   Сформулировать предложения по упрощению модели (например, предварительный pull базовых образов на воркеры, кэширование тестов).
*   **Задача 1.3: Проектирование архитектуры взаимодействия.**
    *   Разработать механизм доставки обновлений из **Приватного репозитория курса** на **Воркеры**.
    *   *Варианты на выбор:* GitOps (воркеры сами пуллят изменения по cron/webhook) или Push-модель (CI/CD приватного репозитория деплоит артефакты задач в S3/Registry, откуда их берут воркеры).

## Фаза 2: Проектирование моделей данных (Data Modeling)
*Цель: Ввести единый стандарт описания задачи, понятный и системе Manytask, и воркерам.*

*   **Задача 2.1: Разработка "Модели Задачи" (Task Model).**
    *   Создать схему (JSON Schema/YAML), которая описывает метаданные задачи.
    *   *Поля:* `task_name`, `language` (python/java/go), `timeout_seconds`, `memory_limit_mb`, `test_files_paths`, `entrypoint`.
*   **Задача 2.2: Разработка "Модели Прогона" (Run Model).**
    *   Стандартизировать формат, в котором воркер отдает результат Manytask-у.
    *   *Поля:* `status` (ok, failed, build_error, timeout), `score`, `stdout`, `stderr`, `execution_time`.

## Фаза 3: Инфраструктура воркеров и таск-раннеров
*Цель: Настроить контроль над репозиторием с раннерами и их окружением.*

*   **Задача 3.1: Настройка репозитория таск-раннеров.**
    *   Создать/реорганизовать репозиторий для хранения конфигураций воркеров.
    *   Настроить CI/CD для автоматической сборки базовых Docker-образов для воркеров (образы, в которых уже установлены нужные версии Python, Java, Go).
*   **Задача 3.2: Механизм синхронизации воркеров.**
    *   Реализовать логику, по которой воркеры узнают о новых задачах (парсинг приватного репозитория курса, чтение `Task Model` из конфигов).
    *   Обеспечить изоляцию (чтобы тесты одной задачи не влияли на другую, очистка окружения).

## Фаза 4: Разработка тонких оберток (Unified Language Wrappers)
*Цель: Сделать запуск тестов для любого языка одинаковым для внешнего оркестратора.*

*   **Задача 4.1: Создание универсального интерфейса (Entrypoint).**
    *   Написать скрипт-обертку (например, `run.sh` или `runner.py`), который будет лежать в корне воркера и принимать стандартизированные аргументы (путь к коду студента, путь к тестам админа).
*   **Задача 4.2: Имплементация обертки для Python.**
    *   Настройка запуска через `pytest`.
    *   Перехват результатов `pytest`, маппинг в "Модель Прогона" (из задачи 2.2).
*   **Задача 4.3: Имплементация обертки для Java.**
    *   Настройка компиляции (`javac` / `maven` / `gradle`) и запуска через `JUnit`.
    *   Обработка ошибок компиляции (вывод понятных логов студенту) и маппинг результатов в единую модель.
*   **Задача 4.4: Имплементация обертки для Go.**
    *   Настройка запуска через `go test`.
    *   Обработка паник (panic) и маппинг результатов тестирования в единую модель.

## Фаза 5: Интеграция, стабилизация и тестирование
*Цель: Добиться того самого "Стабильного запуска", заявленного в глобальной задаче.*

*   **Задача 5.1: Интеграционное тестирование.**
    *   Провести полный цикл (End-to-End): Админ пушит задачу -> Воркер обновляется -> Студент шлет код -> Manytask отдает воркеру -> Обертка запускает -> Manytask получает оценку.
*   **Задача 5.2: Тестирование безопасности и лимитов (Sandboxing).**
    *   Проверить, что `timeout` работает корректно (бесконечные циклы убиваются).
    *   Проверить лимиты памяти (OOM Killer корректно рапортует об ошибке, а не ломает воркер).
    *   Проверить, что студенческий код не может прочитать чужие файлы или ответы к тестам на воркере.
*   **Задача 5.3: Нагрузочное тестирование.**
    *   Сымитировать дедлайн (сотни одновременных отправок решений). Убедиться, что очередь работает стабильно, а воркеры масштабируются или корректно держат нагрузку.

## Фаза 6: Документация
*Цель: Описать новую систему для админов курсов и будущих разработчиков.*

*   **Задача 6.1: Документация для администраторов курсов.**
    *   Как правильно складывать задачи в приватный репозиторий.
    *   Как писать конфигурацию `Task Model` для своих задач.
*   **Задача 6.2: Техническая документация.**
    *   Описание новой архитектуры.
    *   Инструкция: "Как добавить поддержку нового языка программирования (например, C++ или JavaScript), используя тонкую обертку".

---

### Оценка рисков и рекомендации к выполнению:
1. **Безопасность (Security):** Самый большой риск в таких системах — удаленное выполнение чужого кода (RCE). Обертки *обязательно* должны запускать код студента от имени пользователя с минимальными правами (`nobody`) внутри жестко ограниченного Docker-контейнера.
2. **Время холодного старта:** При упрощении модели постарайтесь уйти от сборки Docker-образа *на каждый* сабмит студента. Лучше использовать заранее запущенные "теплые" контейнеры или запускать код внутри уже готового образа, подмонтировав файлы как Volume.
